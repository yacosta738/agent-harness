# Shared Hard Rules — Security Skills

These rules apply to every security skill in this folder. Read them before applying
any skill-specific hard rules.

## 1. Evidence before assertions

- Never claim a finding, vulnerability, or fix exists without a `path:line` anchor
  or a reproducible artifact.
- A scanner label is a claim, not proof. Code reading and runtime reproduction are
  proof.
- Do not invent attack chains the code does not support. If the chain has gaps,
  document them as `proof_gaps` and treat the finding as `needs_review`.

## 2. Trust boundaries first

- Identify the trust boundary before tracing source → sink. Without a boundary,
  the path is just a function call.
- A reachable dataflow is not enough. `confirmed` requires both:
  1. the vulnerable condition is statically reachable under stated preconditions
  2. the source crosses an intended security boundary for a shipped surface
- Local-only, test, fixture, example, vendored, or generated code is not in scope
  unless the repository evidence shows it ships as part of the product surface.

## 3. Repository policy is authoritative

- Read `SECURITY.md`, `../../../agents/ORCHESTRATOR.md`, threat models, and disclosure policy before
  promoting a finding to `confirmed`.
- If `SECURITY.md` and available local product evidence do not establish the
  intended product surface, untrusted input boundary, or trusted operator inputs,
  ask targeted operator-context questions before assigning a verdict.
- Treat hardcoded secrets, weak crypto, missing headers, and similar hygiene
  issues as `low`/`ignore` unless they directly enable a high/critical impact.

## 4. No silent coverage drops

- Every candidate finding that reaches a phase must leave a receipt in its
  candidate ledger (or the equivalent in our setup: in the session report and
  the skill output).
- Coverage rows may close as `reportable`, `suppressed`, `not_applicable`, or
  `deferred` — never silently omitted.
- A "needs more time" decision is `deferred`, not `confirmed`.

## 5. No autonomous destructive actions

- Never run the app, deploy, push, mutate Jira/Linear, or create issues without
  explicit user approval during the current run.
- Never edit repository files unless the active skill explicitly authorizes it
  (for example, `fix-finding` writes the fix; everything else is read-only).
- Never broaden scope into unrelated cleanup or refactors.

## 6. Subagent discipline

- For multi-worker workflows (deep scans, parallel discovery), each worker owns
  one assigned slice and writes only to its assigned paths.
- Coordinator agents are orchestration-only during active rounds: they may
  resolve paths, monitor progress, verify artifact existence, and check schema
  conformance. They must not perform repository-specific discovery, sink
  hunting, candidate generation, or validation prep grounded in target code
  before the round closes.
- Workers must not read, reuse, or overwrite outputs from sibling workers in
  the same round.

## 7. Runtime validation over code inspection

- Prefer runtime reproduction (failing test, crashing PoC, debugger trace,
  valgrind/ASan) over static reading whenever feasible with bounded effort.
- Setup errors are intermediate blockers to investigate, not automatic
  suppression evidence. Repair setup with targeted commands before giving up.
- A slow command with progress signals is not a failed command. Check process
  status, recent logs, artifact timestamps, or resource usage before deciding
  it is blocked.

## 8. Output contracts are mandatory

- Every skill in this folder defines an `## Output Contract`. Honor it exactly:
  include all listed fields, in the listed shape, with the listed types.
- When the contract calls for evidence, give a `path:line` anchor plus a
  short quote or reasoning line. Generic "see above" pointers are not
  evidence.

## 9. Severity calibration is evidence-driven

- `critical` and `high` require a clear exploitation path with major security
  impact (RCE, account takeover, auth bypass, sensitive data exfiltration,
  supply-chain compromise, etc.) reachable from an in-scope attack surface.
- Do not keep `critical`/`high` based on contrived, highly speculative, or
  edge-case-only exploit stories.
- If the issue is a real bug but not a security vulnerability, classify as
  `ignore` (or `low` if it has minimal security relevance).
- If the scanner claim is provably wrong, classify as `ignore` and explain
  the contradiction in plain language.

## 10. No AI attribution

- Conventional commits only. Never add `Co-Authored-By`, `Generated by`, or
  similar AI attribution trailers.
- Commit messages must describe the change, not the tool that wrote it.
